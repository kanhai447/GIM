## 3. 文档结构

新建 docs/interview/design-questions.md，按以下结构。先输出完整目录，再逐节填充；每节完成后自检引用是否真实。

### 第 0 节：使用说明

- 本文档用途：面试前复习、被追问时定位答案。
- 与 architecture-deep-dive.md 的关系：深度文档讲“是什么/在哪”，本文档讲“为什么/被问怎么答”。
- 阅读方式：按功能查；每个功能先看“一句话回答”，再看细节。
- 诚实边界：已知边界在每节末尾，主动说比被问出来好。

### 第 1 节：一分钟项目介绍

- 项目定位、技术栈、服务边界、V2 范围（引用 v2-scope.md）。
- 三个可讲的亮点：消息可靠性（clientMsgId + ACK + session）、文件流式与授权、好友上线提醒单机语义。
- 三个主动说明的边界：多实例 Presence 未做、完整性能阶梯未跑、部分 E2E 脚本未入库（K-17）。

### 第 2 节：横向问题（先讲全局，再讲功能）

每个横向问题按固定结构：问题 → 一句话回答 → 展开 → 追问 → 边界。

必须覆盖：

- Gateway 信任边界：为什么 V1 调 Auth 而不是本地验签；如何防伪造 User-ID/Role；内部服务为什么不能暴露公网。
- 并发模型：Hub 单写、readPump/writePump、慢客户端摘除、为什么业务层不能直接写 Conn。
- 幂等与 ACK：clientMsgId 唯一约束、ACK 只在事务成功后、重复发送返回原消息。
- 事务边界：消息 + session、好友同意、文件对象 + 用户文件；哪些操作不在同一事务及原因。
- 锁顺序与死锁：session 按 user_id 升序、1213 有界重试、Admin 删除同序；Group 无重试是已知边界（A5）。
- 错误码体系：11xx/22xx/24xx 分段、Admin 独立段（A4 修复后）、前端如何消费。
- migration 与索引：版本化、dirty 保护、无 AutoMigrate、关键唯一约束（clientMsgId、session、group_members）。
- 部署边界：Gateway 唯一入口、内部 API/RPC 不暴露、Compose 服务数与一次性 job。
- V2 范围：已实现四 Phase、V2 后期/不做项、为什么不做（引用 v2-scope.md）。

### 第 3 节：按功能的设计问答（主体）

对 architecture-deep-dive.md 第 4 章的 16 个功能，每个功能一节，按固定结构：

```markdown
### 功能：<名称>

**一句话回答**
- 用 2–3 句话说明这个功能怎么实现、最关键的设计点。

**需求与约束**
- 业务需求、技术约束（V1 固定决策、单机、无多实例等）。

**方案**
- 引用深度文档的文件/函数，列出调用链要点，不重复代码细节。
- 关键数据结构、表、Redis key。

**关键决策与理由**
- 为什么这样设计，而不是另一种。
- 至少 2–3 条，每条一句“选择 X，因为 Y，代价是 Z”。

**权衡**
- 性能/一致性/复杂度/可维护性的取舍。

**失败模式与恢复**
- 进程崩溃、DB 失败、推送失败、Redis 不可用、Kafka 不可用。
- 每种失败如何恢复，是否丢消息。

**常见追问与回答要点**
- 至少 5 个追问，每个给回答要点（不写长篇）。
- 示例：多端怎么办？重复发送怎么办？ACK 丢了怎么办？session 和动态聚合的区别？为什么不用服务端生成 ID？

**已知边界**
- 引用 `known-issues.md` 编号（K-14、K-15、K-16、A5、E-8、E-9 等）。
- 主动说明，不回避。
```

必须覆盖的功能（与深度文档第 4 章对齐）：

- 注册、登录、注销、JWT、logout 黑名单
- 用户资料、Admin 用户管理
- 好友搜索、申请、同意/拒绝、列表、备注、删除、详情
- 私聊文本消息
- 私聊图片消息
- 私聊普通文件消息
- 私聊撤回
- 群创建、成员、角色、邀请、申请、禁言
- 群文本/图片/文件消息
- 群撤回
- session 列表、未读、已读、置顶、删除
- 文件上传与下载授权
- 好友上线提醒
- Admin 私聊审计、群管理、文件管理、设置、日志
- 审计日志（每请求 LogEvent、脱敏、Kafka、consumer 幂等）
- migration 与 runner

重点加深（其他功能可简洁）：私聊可靠性、session/unread、文件流式与授权、撤回与授权联动、好友上线提醒、Admin 权限、审计脱敏。

### 第 4 节：故障与边界专题

按“如果……怎么办”组织，每个给回答要点：

- 服务端 ACK 后进程崩溃，消息会丢吗？
- 接收方离线，消息怎么恢复？
- 推送失败，发送方会知道吗？
- Redis 挂了，Presence 和好友通知会怎样？
- Kafka 不可用，审计会怎样？
- 并发发消息和 Admin 删除同一会话，会死锁吗？
- 并发不同 clientMsgId 撤回同一消息，会怎样？（K-14）
- 文件上传中途失败，会留下垃圾吗？
- 退群后还能下载群历史图片吗？浏览器缓存呢？（E-9）
- 多实例部署，好友上线提醒会怎样？（K-15）

### 第 5 节：主动说明的边界

- 多实例 Presence 未做（K-15）。
- 完整性能阶梯、soak/restart、远端 CI 未跑（validation-status.md）。
- 部分 E2E 脚本未入库（K-17）。
- Group 无 1213 重试（A5）。
- 删除表未使用、HideSession 未接线（A1/A2）。
- 撤回并发可能两条（K-14）。
- offline 事件 best-effort（K-16）。
- 文件授权查询无索引、无速率限制（E-8）。

每条给一句话“为什么可以接受/后续怎么补”，不展开成长篇。

### 第 6 节：简历表述建议

- 可写的：真实实现的功能、真实验证项、可解释的设计。
- 不可写的：百万连接、全量压测、分布式 WS 路由、多实例 Presence。
- 给 3–5 条简历 bullet 示例，每条都能在代码/文档中找到依据。

## 4. 质量要求

- 引用必须真实：文件路径、函数名、known-issues 编号、validation-status 项，全部可核对；不确定标注“见深度文档第 X 节”。
- 不重复深度文档：深度文档讲“在哪、怎么串”，本文档讲“为什么、被问怎么答”。
- 每个功能至少 2 条关键决策、5 个追问；重点功能可更多。
- 不虚构：没做的、没验证的、已知边界，全部如实写。
- 控制篇幅：主体是第 3 节，每个功能 30–60 行；横向问题和故障专题简洁。
- 口径一致：与 v2-scope.md、validation-status.md、known-issues.md 不矛盾；如有矛盾，以这三份为准，并在操作日志记录。

## 5. 执行方式（分批提交）

